## 02. 전체 흐름을 먼저 이해하세요

이 서비스는 **AI 앱에 일을 요청하고, 사이트에서 사람이 검토하고, 승인된 결과를 장부에 반영하는 구조**입니다.

~~~text
운영자: 원격 DB·인증·메일·서버 준비
                 ↓
사용자: 사이트 가입·이메일 인증·로그인
                 ↓
사용자: Codex 또는 Claude에 같은 MCP 주소 연결·허용
                 ↓
AI 앱: 연결·회사 확인 → 기존 ERP 거래와 증빙 조회
                 ↓
AI 앱 + 회계 엔진: 근거 검토 → 분개 초안 → 독립 검증 → 승인 요청
                 ↓
사용자: 사이트에서 전표·증빙·금액을 직접 확인 → 승인 또는 반려
                 ↓
AI 앱 + DB: 승인 상태·내용 hash 재확인 → 원자적 전기 → Posted 확인
                 ↓
회계 엔진: 총계정원장 → 시산표 → 재무상태표·손익계산서
                 ↓
필요한 경우: 대사·감사 → 월말 수정분개 → 다시 사용자 승인 → 기간 마감
~~~

**‘도구 실행 허용’, ‘AI 앱 연결 허용’, ‘전표 승인’은 서로 다른 결정입니다.** 앱 연결을 허용해도 전표가 자동 승인되지는 않습니다. 전표를 승인해도 곧바로 장부에 반영되지는 않습니다.

## 03. 누가 무엇을 하나요?

| 담당 | 하는 일 | 직접 하지 않는 일 |
| --- | --- | --- |
| 사용자 | 가입·앱 연결 동의·업무 요청·증빙 확인·전표 승인/반려 | 차대변 합산과 반복 계산을 손으로 처리할 필요가 없습니다. |
| Codex·Claude | 요청 해석·역할 선택·도구 호출·근거 설명·결과 정리 | 사용자 대신 웹 승인 버튼을 누르거나 DB 성공을 추정하지 않습니다. |
| 단일 MCP 서버 | 권한 있는 요청을 공통 ERP·회계·공공자료 서비스에 전달 | 별도 AI 모델을 실행하거나 밤새 자율 업무를 돌리지 않습니다. |
| 회계 엔진·PostgreSQL | Decimal 계산·계정/차대변/기간/증빙 검증·승인 확인·전기·집계 | 법률 조문만으로 모든 회계·세무 판단을 확정하지 않습니다. |
| Cloudflare | 공개 화면과 인증된 원격 요청 처리 | 공공 샘플을 각 사용자의 실제 게시 장부로 취급하지 않습니다. |
| 운영자·개발 담당 | 연결 정보·인증·메일·배포·장애 대응·회귀 검증 | 방문자에게 운영자 API 키와 DB 비밀번호를 배포하지 않습니다. |

방문자는 원격 운영이 활성화된 경우 **소스·Node.js·DB·MCP 서버·공공 API 키를 PC에 설치하지 않습니다.** 사용 가능한 AI 앱과 본인 계정은 필요하고, 그 앱에서 MCP 연결 설정은 한 번 해야 합니다.

## 04. 운영 준비 — 일반 방문자는 건너뛰세요

이 단계는 서비스를 올리는 운영자와 개발 담당의 일입니다.

| 순서 | 운영자·사용자가 제공할 것 | 개발 담당이 수행할 것 | 완료 기준 |
| --- | --- | --- | --- |
| 1. DB 연결 | Supabase Connect의 올바른 접속 문자열·DB 비밀번호, 공개 CA 파일 | 연결·TLS·인증 확인 | DB 접속 검사 성공 |
| 2. 인증·메일 | Supabase Email provider·이메일 확인·허용 redirect URL, 실제 발송 가능한 메일 설정 | 로그인·메일·세션 동작 점검 지원 | 실제 새 계정의 인증·로그인 성공 |
| 3. 원격 배포 | 기존 Cloudflare 접근과 서버 측 키 설정 | schema 검증·원격 migration·secrets 등록·동일 Worker 활성화 | 원격 설정 활성화와 인증된 MCP 응답 확인 |
| 4. 수용 검증 | 본인 인증·앱 연결 동의·전표 최종 승인 | 실제 두 계정 격리·도구 호출·게시 결과 확인 | 승인 전 거절, 승인 후 Posted, 타 계정 변화 없음 |

운영자 설정은 **.env.local의 LEDGERFLOW_DATABASE_URL**을 사용합니다. Supabase 로그인 비밀번호와 DB 비밀번호는 다를 수 있습니다. 접속 문자열의 [YOUR-PASSWORD] 전체를 대괄호 없이 실제 DB 비밀번호로 바꾸고, 비밀번호의 특수문자는 URL 인코딩합니다. 비밀번호는 채팅·문서·GitHub에 보내지 않습니다. 방문자는 이 설정을 할 필요가 없습니다.

일반 방문자에게 이메일 인증을 제공하려면 메일 발송 준비도 필요합니다. Supabase 기본 SMTP는 프로젝트 팀 외 주소의 발송을 제한하므로 일반 가입자용 설정을 별도로 확인합니다. [Supabase 공식 SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)

운영자가 실행할 주요 명령:

~~~sh
pnpm supabase:check
pnpm check
pnpm remote:deploy
~~~

기존 schema와 맞지 않으면 초기화하지 않고 멈춥니다. 원격 배포는 연결 검증 후 기존 schema와 추가 migration을 검증하며 진행합니다. 최초 실제 로그인 시 해당 계정의 가상회사가 만들어집니다.

배포 스크립트가 Cloudflare Hyperdrive에 Supabase CA와 호스트명 검증을 설정하고 SQL 응답 캐시를 끕니다. 로컬 Node의 인증서 파일 설정은 그대로 유지합니다. 방문자가 인증서나 DB 비밀번호를 설치할 일은 없습니다. 운영자는 [원격 사용·배포 상세](REMOTE_USAGE.md)를 참고하세요.

**배포 명령 구분:** remote:deploy는 원격 장부 활성화 경로입니다. site:deploy는 공개 미리보기 배포이며 원격 기능을 끕니다. 현재 코드의 소규모 체험 작업공간 상한은 25개입니다.

## 05. 사용자 첫 단계 — 가입하고 내 장부 열기

원격 기능이 활성화된 뒤의 절차입니다.

1. 공개 사이트를 열고 상단 **로그인·시작하기**를 선택합니다.
2. 처음이라면 **처음 방문·회원가입**을 선택하고 본인 이메일과 비밀번호를 입력합니다.
3. 수신한 확인 이메일의 링크로 이메일을 인증합니다.
4. 사이트로 돌아와 로그인합니다. 인증 링크를 눌렀다는 사실과 사이트에 로그인된 상태는 별도로 확인합니다.
5. 계정별 **한빛유통 주식회사**와 연습용 원천 거래 1,000건이 준비됩니다.

서버는 확인된 로그인 신원을 기준으로 회사를 선택합니다. AI 대화창에 ‘회사 ID를 B의 ID로 바꿔라’고 요청해도 다른 사람의 장부 권한이 생기지 않습니다.

**완료 기준:** 사이트에 내 이메일이 표시되고 개인 장부를 조회합니다. 아직 아무 전표도 게시하지 않았다면 재무 보고서가 ‘장부 반영 전’인 것은 정상입니다.

## 06. AI 앱 연결 — Codex와 Claude 중 하나면 됩니다

사이트의 **AI 연결·계정 관리**에서 원격 MCP 주소를 복사합니다. 두 앱에 연결해도 서버 제품은 ledgerflow-accounting-mcp 하나입니다.

### Codex를 사용하는 경우

사용 중인 앱의 MCP 설정에서 원격 HTTP 서버와 URL을 추가하고 OAuth 로그인을 진행합니다. 화면 이름은 제품 버전과 관리자 정책에 따라 다를 수 있습니다.

이미 Codex CLI를 사용하는 사람은 다음 명령으로 등록·인증할 수 있습니다.

~~~sh
codex mcp add ledgerflow-accounting-mcp --url https://ledgerflow-public-reference-gateway.eric5833.workers.dev/mcp
codex mcp login ledgerflow-accounting-mcp
~~~

[공식 OpenAI MCP 연결 안내](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

### Claude Code를 사용하는 경우

이미 Claude Code를 사용하는 사람은 다음 명령으로 같은 서버를 등록합니다.

~~~sh
claude mcp add --transport http ledgerflow-accounting-mcp https://ledgerflow-public-reference-gateway.eric5833.workers.dev/mcp
~~~

이후 Claude Code의 /mcp에서 인증합니다. Claude 웹·데스크톱은 사용 중인 계정이 원격 사용자 지정 커넥터를 지원할 때 같은 URL을 추가할 수 있습니다. 모든 제품·요금제에서 가능하다고 보장하지 않습니다. [공식 Claude Code MCP 안내](https://code.claude.com/docs/en/mcp)

### 연결 동의와 계정 확인

1. 앱이 연결 인증용 브라우저를 열면 사이트에서 **같은 계정**으로 로그인합니다.
2. 연결할 앱 이름·돌아갈 주소·허용 업무를 읽고 **내 장부 연결 허용**을 선택합니다.
3. 앱으로 돌아와 서버가 연결되었는지 확인합니다.
4. 기존에 같은 이름의 localhost 서버가 등록돼 있다면 URL을 교체합니다. 로컬·원격 항목을 중복 추가하지 않습니다.

연결된 AI는 내 회사의 거래를 읽고 초안·검증·승인 요청을 준비하며, 내가 승인한 전표의 게시를 요청할 수 있습니다. **전표 승인 권한은 주지 않습니다.**

**완료 기준:** 설정에 URL만 저장된 상태를 넘어, 아래 두 도구가 실제로 호출됩니다.

~~~text
연결된 MCP의 get_system_status와 get_company_context를 순서대로 실제 호출해 줘.
서버 이름, 도구 수, 회사 이름, 회사 ID, 공공자료 연결 모드를 알려줘.
거래 생성·분개·승인·장부 반영은 하지 마.
도구가 보이지 않거나 호출이 실패하면 성공했다고 추정하지 마.
~~~

현재 구현 카탈로그는 41개 도구입니다. 원격 실조회 경로를 쓰려는 경우 회사·연결 URL과 공공자료 모드를 확인합니다. 앱 연결 확인은 실제 회계 처리와 별도입니다.

## 07. 이미 있는 거래 1,000건은 무엇인가요?

1,000건은 한 해 동안의 도소매 업무를 연습하도록 미리 만든 **가상 ERP 원천 거래**입니다. 실제 고객 매출, 실제 은행에서 가져온 입출금, 국세청에서 발행받은 세금계산서가 아닙니다.

매출·매입·수금·지급·급여·유형자산·선급비용·미지급비용·수정 항목 등이 포함됩니다. 1월 요청은 이 중 **2026년 1월에 귀속되는 거래**를 조회해 처리하는 일입니다. 새 거래를 입력하는 것이 출발점은 아닙니다.

| 데이터 | 의미 | 재무 보고서에 바로 포함되나요? |
| --- | --- | --- |
| ERP 거래·증빙 | ‘어떤 일이 있었는가’에 대한 원천 자료 | 아니요 |
| 분개 초안 | 그 일을 어떤 계정에 기록할지 준비한 전표 | 아니요 |
| 검증된 전표·승인 대기 | 계산·규칙 확인을 마치고 사람의 결정을 기다리는 전표 | 아니요 |
| 승인됐지만 미게시인 전표 | 사람은 동의했지만 아직 장부 반영 전인 전표 | 아니요 |
| Posted 전표 | 승인 조건을 다시 검사한 뒤 DB에 게시된 전표 | 예 |

그래서 거래가 1,000건 있어도 아직 게시된 전표가 없으면 장부 집계가 비어 있습니다. 사이트는 이를 **‘장부 반영 전’**으로 표시합니다.

## 08. 첫 회계 업무 — 매출 한 건을 요청하세요

처음에는 한 건으로 승인 흐름을 익히는 것이 좋습니다. 요청은 **사이트 입력란이 아니라 연결된 Codex·Claude의 대화창**에 보냅니다.

~~~text
get_system_status → get_company_context로 실제 연결과 회사를 먼저 확인해 줘.
매출 역할로 기존 ERP의 2026년 1월 미처리 매출 한 건을 찾아 줘.
기존 초안이나 게시 전표가 있는지 확인해 중복을 피해 줘.
거래·세금계산서·계약·인도 증빙과 공공 참고자료를 확인해 줘.
분개 초안 생성 → 검증 → 사용자 승인 요청까지만 진행해 줘.
전표 ID·버전·hash, 차변·대변 합계와 계정 선택 이유를 쉽게 설명해 줘.
공공자료의 실제/샘플·시행일·조회 실패·제외 사유와 판단의 불확실성을 알려줘.
사용자가 사이트에서 직접 승인할 때까지 멈춰 줘. 직접 승인하지 마.
작업 결과와 사용 도구 trace를 구조화 Result로 기록해 줘.
~~~

AI는 필요한 역할을 선택하고, 거래 조회·증빙 확인·회계 원천 조회 도구를 호출합니다. 구체적인 계정 매핑과 금액 계산은 회계 엔진에 맡깁니다. 자료가 부족하면 ‘검토 필요’로 남겨야 하며, 무조건 모든 거래를 자동 처리하는 구조가 아닙니다.

**완료 기준:** 거래 ID와 초안·검증 결과·승인 요청이 확인되고, 실제 장부 상태는 아직 Posted가 아닙니다.

## 09. 이때 공공 API 네 개는 어디에 쓰이나요?

분개 대상과 관련 있는 외부 참고자료를 서버가 조회합니다. **운영자 키는 서버에 두고 방문자에게 나눠주지 않습니다.** 공개 샘플 화면은 보관된 예시를 보여주고, 로그인한 원격 장부의 자료 조회·새 분개는 실제 서버 경로를 사용하도록 구현돼 있습니다.

| 기관 | 현재 쓰임 | 반드시 구분할 점 |
| --- | --- | --- |
| 국세청 | 실제 사업자번호가 주어진 거래처의 등록 상태·진위 조회 도구 | 가상 거래처는 실제 번호가 없어 자동 확인을 제외합니다. 네 기관 모두가 매 전표마다 호출되는 것은 아닙니다. |
| 금융감독원 DART | 공시기업 재무·공시 조회, 비교 참고자료 | 공시기업 매출을 한빛유통 매출로 가져오지 않습니다. 선택 기업이 적합한 비교 대상인지 별도 판단이 필요합니다. |
| 국가법령정보 | 거래일에 적용 가능한 세법 조문·시행일 참고 | 현재 조문과 과거 거래일의 적용 조문은 다를 수 있습니다. 법령 조회만으로 회계기준·세무 결론이 확정되지는 않습니다. |
| 한국은행 ECOS | 기준금리·환율·경제통계 참고 도구 | 기준금리는 거래 계약의 이자율이 아닙니다. 모든 통계가 모든 분개 금액에 반영되는 것은 아닙니다. |

분개 초안에는 수집 당시의 참고자료·출처·조회 시각·적용 기준일·실제/샘플·실패/제외 상태가 담깁니다. 이 자료 묶음도 승인 hash에 포함되므로 나중에 새 자료로 승인 내용을 조용히 바꾸지 않습니다.

**완료 기준:** ‘실제 조회 성공’, ‘샘플’, ‘조회 실패’, ‘적용 제외’를 나눠 설명합니다. 키가 등록됐다는 사실이나 예전 성공 기록만으로 현재 요청의 성공을 주장하지 않습니다.

## 10. 초안에서 게시까지 — 전표 상태 읽는 법

~~~text
Draft → Validated → Approval → [사람의 웹 승인] → Posted
 초안      검증 완료     승인 요청                         장부 반영 완료
~~~

사람의 승인 결정은 별도 승인 기록입니다. 화면의 전표 상태가 Approval이어도 승인 기록은 pending/approved/rejected로 달라질 수 있습니다.

| 단계 | 실행 주체·대표 도구 | 통과 조건 | 이 단계가 끝나면 |
| --- | --- | --- | --- |
| Draft | AI 요청 + propose_journal_entry | 지원하는 거래 정책·원천 자료가 있어야 함 | 초안 ID·라인·내용 hash 생성 |
| Validated | validate_journal_entry | 차대변·계정·증빙·거래·기간·중복 검증 | 검증된 전표 |
| Approval | request_journal_approval | 검증된 상태 | 사용자의 독립적인 결정 대기 |
| 승인 결정 | 사용자의 웹 화면 | 대상 전표·내용 hash·권한·유효한 웹 세션 확인 | 승인 또는 반려 기록, 아직 미게시 |
| Posted | get_approval_status → post_journal_entry | 승인·hash·기간·중복을 다시 확인 | 원자적으로 장부 반영, 집계 대상 |

**검증된 전표가 곧 회계 판단이 완벽한 전표라는 뜻은 아닙니다.** 규칙 검사가 통과해도 계약·기간귀속·추정·증빙의 의미는 사람이 검토해야 합니다. K-IFRS 적용 가정과 불확실성을 함께 확인합니다.

## 11. 사람이 사이트에서 직접 승인하기

1. AI가 승인 요청을 준비하면 **같은 계정의 사이트**로 돌아옵니다.
2. **새로고침 → 사용자 승인 → 전표 보기**를 선택합니다.
3. 아래 항목을 대조합니다.
4. 내용이 맞으면 승인하고, 틀리거나 근거가 부족하면 반려합니다.
5. 승인 버튼을 눌렀다는 사실과 처리 성공 응답·승인 상태를 구분합니다. 오류가 보이면 먼저 해결합니다.

| 검토 항목 | 확인할 내용 |
| --- | --- |
| 대상 | AI가 알려준 거래·전표 ID가 맞는가? |
| 버전·hash | 지금 화면의 승인 대상이 AI가 설명한 내용과 같은가? |
| 날짜·기간 | 거래일·인도일·귀속 월이 타당한가? |
| 차변·대변 | 계정과 금액이 증빙과 맞고 양쪽 합계가 같은가? |
| 증빙 | 계약·세금계산서·인도·입출금 자료가 연결돼 있는가? |
| 참고 근거 | 공공자료의 적용일·출처·실패/제외 상태가 설명됐는가? |
| 판단 | 회계기준 가정·불확실성·검토 필요 사항을 이해했는가? |

**AI에게 사이트 로그인 세션을 전달하거나 승인 버튼을 대신 누르게 하지 않습니다.** 웹에서 허용한 앱 연결 권한이나 AI 도구 호출 허용도 이 승인 절차를 대체하지 않습니다.

**완료 기준:** 해당 전표 내용에 연결된 독립적인 approved 또는 rejected 기록이 확인됩니다. 아직 장부 반영을 요청하지 않았다면 Posted로 보고하지 않습니다.

## 12. 승인한 전표만 장부에 반영하기

같은 앱 대화창에서 다음 요청을 보냅니다.

~~~text
get_system_status와 get_company_context로 실제 연결과 회사를 다시 확인해 줘.
내가 사이트에서 승인한 전표 [전표 ID]만 대상으로 해 줘.
전표의 승인 상태·버전·hash가 승인한 내용과 일치하는지 다시 확인해 줘.
조건을 충족하면 post_journal_entry로 장부에 반영해 줘.
DB 결과가 Posted인 전표만 완료로 보고하고, 실패·미승인·반려 건은 따로 알려줘.
2026년 1월 총계정원장·시산표·재무제표를 조회해서 설명해 줘.
회계기간 마감은 지금 하지 마.
~~~

DB는 게시 시점에 승인·권한·기간·중복·내용을 다시 검사합니다. 한 번 게시된 전표를 그대로 덮어쓰지 않습니다. 네트워크 응답이 끊겼다면 같은 작업의 기존 전표 상태를 조회한 후 재시도하고, 새 전표를 무작정 추가하지 않습니다.

**완료 기준:** 실제 DB가 Posted를 반환하고 원장·시산표에 해당 전표가 집계됩니다. AI의 ‘완료했습니다’라는 자연어 답변만으로 완료를 판단하지 않습니다.

## 13. 숫자로 보는 한 건의 변화

아래는 흐름 이해용으로 만든 **설명 예시**입니다. 실제 fixture의 특정 거래나 현재 게시 결과가 아닙니다.

상품을 외상으로 판매했다고 가정합니다. 공급가액 100,000원, 예시 부가세 10,000원, 받을 돈 합계 110,000원, 상품 원가 60,000원입니다. 이 비율과 가정을 실제 세무 판단으로 일반화하지 않습니다.

| 계정 | 차변 | 대변 | 의미 |
| --- | --- | --- | --- |
| 매출채권 | 110,000 | 0 | 고객에게 받을 돈 |
| 상품매출 | 0 | 100,000 | 상품 판매 수익 |
| 부가세예수금 | 0 | 10,000 | 매출과 구분해 기록하는 예시 세액 |
| 매출원가 | 60,000 | 0 | 판매한 상품의 원가 |
| 상품 | 0 | 60,000 | 판매에 따른 상품 재고 감소 |
| 합계 | 170,000 | 170,000 | 차변과 대변 합계 일치 |

- 초안·승인 대기에서는 위 금액이 아직 게시 원장에 들어가지 않습니다.
- Posted 이후에는 위 라인이 원장·시산표 집계에 포함됩니다.
- 이 예시의 판매 수익과 매출원가 차이는 40,000원입니다. 회사 전체 순이익은 다른 비용·전표까지 함께 봐야 합니다.
- 판매했어도 아직 입금받지 않았다면 예금이 늘어난 것이 아니라 매출채권이 생긴 것입니다. 수금은 별도의 은행 거래와 분개로 확인합니다.
- 이 다섯 라인만으로 회사 전체 재무상태표를 만들었다고 해석하지 않습니다. 기초 재고·자본·다른 거래도 필요합니다.

## 14. 월 전체를 처리하는 방법

한 건의 흐름을 확인한 다음 기존 1월 거래 전체를 요청합니다. **같은 승인 절차를 거래별로 반복하는 것**이지, 승인 단계를 생략하는 명령은 아닙니다.

~~~text
get_system_status → get_company_context로 연결·회사·실제 도구를 확인해 줘.
기존 ERP의 2026-01-01~2026-01-31 미처리 거래를 모든 페이지에서 조회해 줘.
총괄·매출·매입·자금·결산·감사 중 필요한 역할을 현재 대화에서 순서대로 적용해 줘.
이미 Posted인 거래는 제외하고, 기존 초안이 있으면 먼저 확인해 중복을 피해 줘.
증빙과 공공자료를 확인해 분개 초안 → 검증 → 사용자 승인 요청까지 준비해 줘.
근거 부족·미지원·실패 건은 검토 필요로 남겨 줘.
거래별 상태, 전표 ID·버전·hash·차대변 합계·위험을 표로 정리하고 Result를 기록해 줘.
사용자 웹 승인 대기에서 멈춰 줘. 병렬 위임과 기간 마감은 하지 마.
~~~

사용자가 사이트에서 검토를 마친 다음:

~~~text
방금 준비한 1월 처리 목록 중 내가 사이트에서 승인한 전표만 확인해 줘.
승인·버전·hash 조건을 재검사해 해당 전표만 장부에 반영해 줘.
DB에서 Posted를 확인한 건, 미승인·반려·실패 건을 따로 정리해 줘.
1월 시산표·재무제표와 남은 미처리 거래·결산 검토 항목을 보여 줘.
회계기간은 아직 마감하지 마.
~~~

대량 요청이 호출 제한이나 앱 이용 한도에 걸리면 이미 처리한 ID와 현재 상태를 보존하고 다음 요청에서 이어갑니다. 모델이나 앱이 중단된 동안 서버가 스스로 나머지를 계속 처리하지는 않습니다.

## 15. 재무 보고서를 읽고 월말 결산하기

사이트의 **재무 보고서**에서 2026-01을 선택하고 새로고침합니다. AI가 말한 기간과 사이트의 선택 기간이 같은지 확인합니다.

| 보고서 | 무엇을 보여주나요? | 집계 범위 |
| --- | --- | --- |
| 총계정원장 | 계정별로 어떤 게시 전표가 들어왔는지 | 조회기간의 Posted 라인 |
| 시산표 | 계정별 차변·대변·잔액과 합계 | 조회기간의 Posted 라인 |
| 재무상태표 | 기준일 현재 자산·부채·자본 | 기준일까지 누적 게시 결과 |
| 손익계산서 | 해당 기간 수익·비용·손익 | 선택한 기간의 게시 결과 |

시산표의 차대변 합계 일치는 필요한 검증이지만, 증빙 누락이나 잘못 선택한 계정까지 모두 정답이라고 보장하지 않습니다.

월말에는 아래 순서로 별도 검토합니다.

1. **자금 역할:** 은행 원천 입출금과 게시된 예금·채권·채무를 대사합니다. ERP 금액과 게시 원장의 차이는 미전기·시점 차이·오류를 나눠 봅니다.
2. **감사 역할:** 중복 후보·증빙 누락·기간 오류·원장 불일치·결산 누락을 조사합니다.
3. **결산 역할:** 자산·선급비용 스케줄에서 감가상각·비용 배분 등 지원되는 수정분개 초안을 준비합니다.
4. **사용자:** 수정분개도 증빙·계산·추정을 확인하고 웹에서 승인합니다.
5. **AI + DB:** 승인된 수정분개를 게시하고 보고서를 다시 조회합니다.
6. **사용자 명시 요청 후:** 해당 기간의 원천·결산 전기 완결성과 권한을 검사해 마감합니다. 기본 업무 요청이 자동 마감을 뜻하지 않습니다.

~~~text
결산 역할로 2026년 1월의 미처리·상각·선급비용 누락과 대사·감사 위험을 확인해 줘.
지원되는 수정분개는 초안·검증·승인 요청까지만 준비해 줘.
계산 근거와 적용 가정, 추가 검토 사항을 알려주고 사용자 승인 대기에서 멈춰 줘.
미지원 항목을 임의로 확정하지 말고 기간 마감은 아직 하지 마.
~~~

법인세 산출·법정 신고·현금흐름표·자본변동표·전체 주석까지 완성된 재무보고 시스템은 아닙니다. 이 프로젝트는 제한된 정책을 구현한 가상회사 포트폴리오이며 완전한 K-IFRS 준수 인증을 주장하지 않습니다.

## 16. 에이전트 여섯 개는 언제 쓰이나요?

| 역할 | 사용 시점 | 주로 남기는 결과 |
| --- | --- | --- |
| 총괄 | 월 범위 설정·업무 순서·의존성·예외 정리 | 구조화 Task·처리 계획·최종 집계 |
| 매출 | 계약·인도·매출채권 검토 | 매출 초안·수익인식 가정·승인 요청 |
| 매입 | 매입 증빙·중복·거래처 검토 | 매입 초안·검토 필요 사항 |
| 자금 | 수금·지급·은행 대사 | 대사 결과·현금 전표 제안 |
| 결산 | 상각·기간말 수정·보고·마감 검토 | 수정분개 초안·보고서·잔여 항목 |
| 감사 | 다른 작업 결과의 위험 조사 | 중복·증빙·기간 위험 보고, 전표 쓰기 없음 |

**여섯 역할이 정의됐다는 것과 여섯 독립 에이전트가 실제 실행됐다는 것은 다릅니다.** 현재 기본 사용은 필요한 역할을 같은 앱 대화에서 순서대로 적용하는 방식입니다.

- 원격 MCP는 초기 instructions와 역할 프롬프트 여섯 개를 제공합니다.
- 앱에 native agent/skill 파일이 자동 설치되는 기능은 아닙니다. 로컬 저장소에는 앱별 정의 파일도 있습니다.
- 병렬·독립 하위 에이전트 실행은 사용자가 명시적으로 요청했을 때만 사용합니다.
- 역할 이름은 인증이나 승인 권한이 아닙니다. 서버가 로그인 신원·회사·실제 scope를 별도로 확인합니다.
- 실제 실행은 앱 실행 내역·MCP trace·역할별 Result를 함께 확인합니다. 역할 이름만 적힌 보고로 독립 실행을 입증하지 않습니다.

정상적인 결과 기록에는 업무 ID, 역할, 상태, 대상 거래, 도구 trace, 발견 사항, 부족한 증빙, 위험, 승인 필요 여부, 실제 게시 여부를 남깁니다. DB 증거 없이 journalPosted=true로 기록할 수 없습니다.

## 17. A와 B가 동시에 사용하면 어떻게 되나요?

| 상황 | 결과 |
| --- | --- |
| 로그인 없이 공개 사이트만 방문 | 같은 조회 전용 샘플을 봅니다. 월·페이지 선택은 각 브라우저 상태입니다. |
| A가 로그인하고 자신의 전표 게시 | A의 원장·보고서에 반영됩니다. B의 장부와 공통 샘플은 바뀌지 않습니다. |
| B가 A의 회사 ID·전표 ID를 입력 | 서버의 회사 바인딩과 DB 권한 검사에서 거절합니다. |
| A가 다른 PC에서 같은 계정으로 로그인 | 원격 운영이 활성화된 경우 자신의 기존 장부를 이어 봅니다. |
| 두 사람이 같은 계정을 공유 | 같은 계정의 장부를 보게 됩니다. 계정 공유는 사용자 분리가 아닙니다. |
| 운영자가 공개 샘플을 새로 배포 | 모두가 보는 공통 샘플은 새 배포 자료로 바뀔 수 있습니다. 개인 장부와는 별개입니다. |

다른 앱 연결을 끊고 싶으면 **AI 연결·계정 관리 → 연결한 앱과 접근 취소**를 사용합니다. 단순 웹 로그아웃과 기존 AI 연결 권한 취소는 다른 일입니다.

## 18. 잘못됐거나 중단됐을 때 이어가는 방법

| 상황 | 확인·재개 방법 |
| --- | --- |
| 사이트가 공개 샘플 모드 | 운영자 DB·인증 준비 단계입니다. 연결 명령을 반복해서 분개 성공을 만들 수는 없습니다. |
| 서버 URL은 저장됐지만 도구가 안 보임 | 실제 연결 주소·로그인·앱 허용을 확인하고 status/context를 다시 호출합니다. |
| 이메일이 오지 않음 | 이메일 오타·스팸함·운영자의 SMTP·제공자 제한을 확인합니다. 이메일 확인을 임의로 꺼서 해결하지 않습니다. |
| AI와 사이트의 회사·전표가 다름 | 같은 로그인 계정·MCP 주소·작업 목록을 쓰는지 확인합니다. |
| 증빙·판단 근거 부족 | 게시하지 않고 검토 필요로 남깁니다. 사람의 보완·검토 후 재개합니다. |
| 공공자료 조회 실패 | 실패와 적용 제외를 구분하고 필요한 검토를 보완합니다. 성공이나 샘플로 바꿔 보고하지 않습니다. |
| 전표를 반려함 | 반려 사유를 보존합니다. 기존 미게시 전표를 허용 조건에서 폐기 표시하고 새 초안으로 다시 검토합니다. |
| 승인 후 내용 hash가 다름 | 기존 승인으로 게시하지 않습니다. 새 승인 대상과 근거를 다시 확인합니다. |
| 게시 요청 중 네트워크 단절 | 기존 전표를 먼저 조회합니다. Posted면 중복 게시하지 않고 그 결과를 사용합니다. |
| 이미 게시한 전표에 오류 발견 | 원전표를 삭제·덮어쓰지 않고 역분개 초안 → 검증 → 별도 사용자 승인 → 게시로 수정합니다. |
| 닫힌 회계기간에 게시 시도 | 마감기간 전기 금지 규칙이 작동합니다. 임의 재개방하지 않고 후속 처리 방식을 검토합니다. |
| 호출 제한·앱 이용 한도·대화 중단 | 처리한 ID·전표 상태·미완료 이유를 남기고 사용자가 새 요청으로 이어갑니다. 자동 백그라운드 재개는 없습니다. |

재개용 요청:

~~~text
이전 업무를 이어서 하되 get_system_status와 get_company_context부터 확인해 줘.
앞서 처리한 거래·전표 ID를 조회해 실제 상태를 먼저 구분해 줘.
Posted는 재처리하지 말고 기존 Draft·승인 대기·반려·실패 원인을 정리해 줘.
미완료 항목만 필요한 단계부터 재개하고 사용자 웹 승인 대기에서는 멈춰 줘.
성공 여부를 추정하거나 SQL·셸로 회계 권한을 우회하지 마.
~~~

## 19. 어느 부분이 자동화되나요?

| 자동으로 도와주는 일 | 사용자가 직접 결정하는 일 |
| --- | --- |
| 권한 있는 거래·증빙 조회, 참고자료 수집과 캐시 | 어떤 기간·대상을 처리할지 요청 |
| 반복 거래의 결정론적 계정 매핑·분개 계산 | 불확실한 계약·증빙·회계 가정 검토 |
| 차대변·계정·기간·중복·참조 무결성 검사 | 앱 연결 동의·실제 전표 승인/반려 |
| 승인된 전표의 조건 재검사·원자적 게시 | 결산·기간 마감의 명시적인 요청 |
| 게시 원장 집계·시산표·보고서 계산 | 실제 업무 적용·전문가 검토가 필요한 판단 |

이 서비스는 별도 유료 LLM API·자체 오케스트레이터·무인 스케줄러를 사용하지 않습니다. AI 추론은 사용자가 연결한 앱이 담당합니다. 앱 구독·이용 한도와 Cloudflare·Supabase·메일 제공자의 요금/용량은 별도이며, 서버가 있다고 모든 이용이 무제한 무료인 것은 아닙니다.

이 사이트를 만든 목적은 **원천 거래가 근거 검토·분개·검증·사람의 승인을 거쳐 장부와 재무 보고서로 이어지는 과정을 체험하는 것**입니다. 실제 세금 신고나 은행 업무를 대신하는 서비스로 소개하지 않습니다.

## 20. 한 번의 업무가 끝났다는 판단 기준

- 연결된 회사·기간·대상 거래를 실제 도구 결과로 확인했습니다.
- 이미 게시한 거래를 제외하고 증빙·공공자료의 출처·적용일·실패/제외를 설명했습니다.
- 초안·검증·승인 요청과 각 전표의 ID·버전·hash를 기록했습니다.
- 사용자가 사이트에서 해당 내용을 직접 승인했습니다.
- 승인 상태와 hash를 재확인한 뒤 DB의 Posted를 확인했습니다.
- 원장·시산표·재무 보고서에 반영된 결과를 조회했습니다.
- 미승인·반려·실패·검토 필요·미지원 항목을 별도로 남겼습니다.
- 역할별 Result와 도구 trace를 기록했고 기간 마감 여부를 분명히 했습니다.

**위 과정의 실제 결과가 있어야 회계 처리가 끝난 것입니다. 이 안내 파일을 열거나 서버를 연결했다는 사실만으로 거래가 처리되지는 않습니다.**
